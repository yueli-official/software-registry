# Catalog and consumer contract

The catalog owns public facts, descriptions, usage instructions, FAQ, documentation links, category keys, image definitions and deterministic source-selection rules for external software. `categories.json` owns category names. A consumer's own products remain in its independent release process. Each definition can be adopted separately; consumers do not need to migrate their entire software portfolio. The first package is the version authority. Every additional package must have the same version. A reference has a homepage and no fictitious package.

The source drivers cover GitHub releases, Scoop manifests, the official Python release API, and a small number of explicit official-source parsers. Scoop download hooks are never executed. Adding a driver requires schema and behavior tests; defining a new software normally adds one JSON file.

A plan records the manifest digest, software/version, original upstream release/asset identity where available, exact package URLs, size and upstream checksums. Byte verification adds calculated SHA256 values, exact size, independent-checksum evidence and an input-plan digest. The digest detects an accidental change to a pinned plan; it is not a cryptographic signature or authorization to publish.

The Python interface is `load_manifest`, `create_plan`, and `verify_plan`. A private consumer validates the manifest/plan association, retains its previous source rules, supplies any required detached-signature verifier, and maps the verified plan to its own publishing API. It decides whether a software is enrolled for automatic updates, permitted for mirrors and approved for first publication.

Consumer-side data includes endpoint and authentication configuration, local software identities, category database mappings, featured placement, local editorial additions, storage policies, publication locks, download caches and receipts. None of it is written back into public definitions. Public descriptions, guides, FAQ and image selections come from the catalog; consumer-specific additions and privately maintained products remain under the consumer's authority.

Icons and screenshots retain original public sources, hashes and provenance. Icons can use inline SVG or a named entry in an original archive; generated name marks are identified separately. Screenshots retain their review and permission evidence. The consumer maps original hashes to its media receipts, renders captions and source links using its own delivery references, and synchronizes references on replacement or removal. Neither media-service identities nor rendered consumer media URLs enter catalog Markdown. Updating content or images is independent of package publication.

`component_fingerprints` separates managed text/category content, icon bytes, screenshot bytes, ordered screenshot presentation and package rules. JSON formatting, object-key order and line-ending conventions do not change these fingerprints. Markdown whitespace inside a line and screenshot order remain significant. Source URLs are provenance, not byte identity; the declared original SHA256 identifies a reviewed image, and consumers verify newly acquired bytes against it. Captions, ordering and removal change references without reuploading unchanged images or directly deleting shared assets.

Fingerprints support comparison; live managed-field differences decide actual writes. Consumers compare desired values, their last confirmed successful projection and current live values. Equal desired/live fields need no write. A live field differing from both its confirmed baseline and desired value is a conflict, including an online edit when the registry is unchanged. Update only owned changed values, preserve unrelated fields and use the target API's concurrency contract when writing. Store confirmed components and projections privately, advance them only after successful readback, and leave an identical receipt untouched on repeated runs.

Missing image receipts do not prove changed bytes. When existing media cannot be matched to confirmed original hashes, consumers restore or reconcile that evidence before uploading; preview must report the uncertainty. New media with a proven changed hash can be acquired separately. An unchanged definition or package-rule fingerprint must never suppress upstream version discovery. Compare discovered release/version and asset evidence independently; conflicting known hashes for an already published version require review rather than silent replacement. Conditional HTTP requests can reduce transfers where supported; an ETag is not necessarily a file checksum. See [change-detection research](change-detection-research.md) for source-backed guidance.

The public tools have no consumer API client or runtime target default. The discovery workflow only reads official public metadata and produces a plan. PR checks run schema/unit tests on hosted runners. Trusted publishing runs in a separate consumer environment and records its own outcome, including uncertain writes.

Schema validation is offline. Actual metadata discovery is bounded and read-only. Verification requires an explicit private state directory, enforces byte/time limits, avoids directory links, and locks the frozen plan while writing. A repeated verifier reuses a cached package only after checking its exact content again.

Official release publication dates, when supplied by the upstream release authority, travel in plans as `upstreamPublishedAt`. Discovery time is never a substitute. A consumer records each software/channel/version once and treats checks, metadata edits and repeated synchronization separately from software releases. The daily read-only discovery currently covers aria2 as the first adopted entry; the public workflow receives no consumer identity or publishing credentials.
