# 软件目录的增量同步与变化判定

调研日期：2026-10-14。本文依据一手资料归纳机制，再提出最小同步建议；未描述特定系统的实现。
建议以公开内容、媒体实际字节和已发现的软件发行作为变化依据，只更新确有差异的部分。
检查时间、回执缺失、下载地址换签名等运行信息变化，不能单独触发内容更新或媒体重传。

## 一手资料中的机制

- HTTP ETag 是选定表示的不透明验证器，不一定是文件哈希；弱 ETag 不保证字节相同。
  条件 GET 可使用 `If-None-Match` 减少传输；`If-Match` 使用强比较防止覆盖并发修改。
  依据：[RFC 9110 §8.8.3、§13.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1)。
- Git 以内容寻址组织对象，内容标识与文件名、路径的作用不同。
  可借鉴“先识别内容，再建立引用”，但不能把 Git 对象 ID 当作裸文件的 SHA-256。
  依据：[Git 官方内容寻址说明](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)。
- Scoop 区分版本发现 `checkver` 与生成更新 `autoupdate`，可在软件定义不变时发现上游新版本。
  因而注册文件没有修改，不代表上游发行没有变化。
  依据：[Scoop 官方自动更新文档](https://github.com/ScoopInstaller/Scoop/wiki/App-Manifest-Autoupdate)。

## 建议：分别比较四类内容

| 类别 | 比较依据 | 变化后执行 |
| --- | --- | --- |
| 文字与元数据 | 目标中实际展示、由同步方管理的字段值 | 只更新有差异的字段 |
| 图标 | 准备引用的原始文件字节 SHA-256 | 摘要不同才获取或上传新媒体 |
| 截图 | 有序列表中的图片摘要、选择、说明等展示字段 | 字节变化获取媒体；顺序或说明变化只修改列表 |
| 软件包 | 发现后的版本，以及每个平台资产的字节 SHA-256 | 版本变化更新发行信息；字节变化才传输新包 |

字段比较前按合同统一类型、默认值与序列化；忽略 JSON 缩进、对象键顺序及运行时间戳。
不能随意删除正文空白或排序截图；标签仅在合同明确视为集合时排序，缺失、空值与空字符串也由合同决定。
摘要可用于快速筛选，更新计划仍应列出字段差异，不能因为整体摘要变化就替换全部字段和媒体。

## 建议：图片字节去重与展示关系分开

对实际读取的完整图片字节计算 SHA-256，保存“摘要 → 已确认可复用媒体”的映射。
相同字节可复用同一媒体；文件名或来源 URL 改变并不意味着图片改变，同一 URL 也可能返回新字节。
图片重编码、压缩或元数据变化会改变字节摘要，即使肉眼相似；这里不采用感知相似度去重。
若存在图片转换，分别记录原件摘要和转换结果摘要，并固定转换规则，避免混用两种身份。
截图从同一组图片中改变选择、顺序或说明时，保留媒体引用，只更新有序展示关系。
移出截图列表不等于立即删除底层媒体；共享引用的回收需要另行确认。
上述为内容寻址原则的设计应用，不是 Git 文档规定的媒体接口。

## 建议：最后成功状态与当前在线状态分开

记期望内容为 D、最后确认成功的内容为 B、当前读取的在线内容为 O；按管理字段分别判断。

| 条件 | 判定 |
| --- | --- |
| D = O | 无需写入；必要时补齐同步记录 |
| D ≠ B，O = B | 期望内容变化，可生成最小更新 |
| D = B，O ≠ B | 在线发生漂移；报告或按明确的字段归属政策处理 |
| D ≠ B，O ≠ B，D ≠ O | 双方均改变，停止冲突字段的自动覆盖 |
| 缺少 B 或无法确认 O | 证据不足，先读取或恢复，不能宣称“媒体已变化” |

B 是最后成功的基线，不是当前在线事实；定期或写入前读取 O 才能发现人工修改和资源失效。
只比较同步方拥有的字段，保留其他管理者的内容；漂移修复也应先形成字段级差异。
批次部分失败时，仅对已确认成功的部分推进基线，不能把期望值整体记为成功状态。

## 建议：丢失回执先恢复证据

回执记录字段快照、媒体摘要与引用、发行摘要、目标修订标识和确认结果；不参与公开内容摘要。
回执丢失只能说明本地证据缺失，不能证明图标、截图或软件包的字节发生变化。
先读取在线字段及媒体引用，查询可用的摘要信息，或在允许读取原件时重新核对字节。
内容一致则补回执；同摘要媒体存在则复用；已有媒体失效属于引用修复，不应描述为图片变更。
无法确认媒体身份时报告“未知”并停止盲目重传；“未找到记录”不能自动等同于“媒体不存在”。

## 建议：条件读取与条件写入

条件 GET 收到 304 时复用对应缓存；没有可用缓存则重新取得完整表示，不能凭空得到文件摘要。
弱 ETag 的 304 表示缓存验证成功，不是新旧字节相同的独立证明；严格字节核对仍依赖可靠摘要或重新读取。
目标接口支持强 ETag 时，读取 O 后携带该 ETag 的 `If-Match` 写入，防止比较后被其他操作修改。
收到 412 则重读并重算差异，不去掉条件强行覆盖；弱 ETag 不可用于强比较保护。
ETag 改变可能源于无关字段，应重读后判断管理字段，而不是直接触发全量更新。
这些语义见上述 RFC；接口是否提供有效的条件写入能力必须单独确认。

## 建议：无变化不写入，上游仍需检查

即使注册文件和 B 都未改变，也要按检查策略继续发现上游版本与资产，再形成新的 D。
版本相同但包摘要不同属于同版本替换，应作为异常确认；版本不同但包摘要相同只需更新相应发行信息。
一次检查无变化可记录检查结果，但不修改公开内容、不重传媒体、不重复创建发行。
最小闭环是“发现 → 读取 → 字段及字节比较 → 条件更新 → 确认 → 保存成功基线”。
